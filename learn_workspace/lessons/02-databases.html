Databases from the ground up, using tiga/store.py

Tiga remembers leads, drafts, suppressions, issues and reports in one SQLite file. This lesson walks the data model from first principles and shows why each design choice exists.

1. What a database is for

Memory vanishes on restart and files do not protect you from two writers at once. A database gives you durability (data survives crashes), concurrency control (writers do not corrupt each other) and queries (ask questions without scanning by hand). SQLite is a full relational database in a single file with no server, which is perfect for one user and a good way to learn the model.

2. Tables, rows, keys

CREATE TABLE issues (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'open',
  dedupe_key TEXT NOT NULL UNIQUE,
  occurrences INTEGER NOT NULL DEFAULT 1 );
  • Primary key: identifies a row. id here.
  • NOT NULL / DEFAULT: the database refuses bad data, so code does not have to re-check everywhere.
  • UNIQUE: dedupe_key means the same bug cannot be filed twice. The rule lives in one place and holds even if two requests race.

3. Constraints beat "check in code first"

A common beginner pattern is if not exists: insert. With two concurrent callers both see "not exists" and both insert. A UNIQUE constraint makes the database decide atomically. Look at claim_job:

INSERT OR IGNORE INTO job_runs (job_name, run_date, claimed_at) VALUES (?, ?, ?)
-- rowcount == 1  -> you got the claim
-- rowcount == 0  -> someone already has it

That one statement is why a restart or double fire cannot send two daily reports. It is the idempotency pattern: do the claim first, then the work; release the claim if the work fails so it can be retried.

4. Transactions and ACID

A transaction groups statements so they all happen or none do. ACID: Atomic (all or nothing), Consistent (constraints hold), Isolated (concurrent transactions do not see each other's half-done work), Durable (committed means on disk). In store.py every write uses with self._db:, which commits on success and rolls back on an exception. transition_issue reads the status, checks the allowed move, updates and writes the audit row inside one transaction, so the audit log can never disagree with the data.

5. State machines in data

ISSUE_FLOW is a dictionary of allowed moves (open to triaged to approved and so on). Putting the only status-changing function in the store gives locality: every rule about statuses lives in one place, so a bug cannot hide in some route handler. The test test_dev_cannot_start_before_user_approval pins the rule that matters most.

6. Indexes

An index is a sorted side-structure (a B-tree) that lets the database find rows without scanning the whole table. Primary keys and UNIQUE columns get one automatically. Add an index when a query filters or sorts on a column and the table is large; every index slows writes and uses space. For outreach, searching by email and status would justify one once there are tens of thousands of rows. Use EXPLAIN QUERY PLAN SELECT ... to see whether the database scans or searches.

7. Concurrency in SQLite: WAL

By default a writer blocks readers. Write-ahead logging (PRAGMA journal_mode=WAL) appends changes to a log, so readers keep reading the last committed state while one writer writes. It is still one writer at a time, which is a real limit: it is why a multi-user hosted Tiga would move to PostgreSQL, which adds row-level locking and many concurrent writers.

8. SQL injection and parameters

Notice VALUES (?, ?, ?) everywhere. Values are passed separately from the SQL text, so a recipient named x'); DROP TABLE outreach;-- is just a string. Column names cannot be parameters, which is why update_outreach checks field names against a whitelist before building the statement.

9. Normalisation and trade-offs

Normalising means storing each fact once. We keep company inside each outreach row, which is mildly denormalised: simple, and fine at this size, but if the same company had many contacts you would add a companies table and a foreign key. Knowing when to denormalise, and saying why, is a senior-level answer.
